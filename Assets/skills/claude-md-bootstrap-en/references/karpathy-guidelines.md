# Karpathy-Inspired Behavioral Guidelines

Source: https://github.com/forrestchang/andrej-karpathy-skills

These 4 principles MUST be embedded verbatim in any CLAUDE.md generated by this
skill. Do not paraphrase or localize them — the original wording is precise
and any rewording introduces semantic drift.

When embedding, only the section header and a single-line intro are authored by
this skill. The 4 principles themselves are copied verbatim.

---

## Verbatim content to embed

```markdown
**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

### Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
\```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
\```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
```

## Why these 4 principles work

| Principle | What it prevents |
|-----------|------------------|
| Think Before Coding | AI silently picking one interpretation when the request is ambiguous, then doing the wrong thing |
| Simplicity First | AI adding 200 lines of speculative "flexibility" when 30 lines would solve the problem |
| Surgical Changes | AI "improving" adjacent code that wasn't broken, creating massive diffs that mix concerns |
| Goal-Driven Execution | AI claiming "done" without verification — TDD-equivalent at the planning level |

Together they form a behavioral floor: AI is biased toward asking, simplifying,
not touching unrelated code, and verifying its own work. This is complementary
to (not redundant with) Spec-Kit's planning discipline and Superpowers'
test-driven-development skill.

## Why the wording is not reworded

1. **Loss of precision** — "Surface tradeoffs" / "Surgical changes" / "Loop until verified" have specific meanings that get diluted when reworded
2. **LLM behavior** — models follow these imperative instructions more reliably in their original form
3. **Karpathy's original intent** — the wording was tested against real LLM coding failures; deviation from the verbatim text reduces effectiveness
4. **Community alignment** — these 4 phrases are widely circulated verbatim; staying verbatim makes the project's CLAUDE.md instantly recognizable to other developers

The intro line should explain why this section exists, but the principles
themselves stay verbatim.
